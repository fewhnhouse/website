# Felix Website

This repository is Felix Wohnhaas' personal website. The core concept is a portfolio presented as a desktop environment called FelixOS: visitors land on a simulated operating-system shell with desktop shortcuts, draggable windows, a dock, and individual "apps" for different parts of Felix's work and life.

The goal is not a conventional marketing portfolio. Build features as useful desktop apps and windows that feel like opening a personal machine: direct, polished, technical, and grounded in real content.

## Project Shape

- `src/routes/` contains TanStack Router file routes. Desktop apps that should be directly addressable usually get a route like `src/routes/skills.tsx`; the route component can return `null` because the root route renders the desktop shell based on the pathname.
- `src/routes/__root.tsx` owns the document shell and maps routes to desktop app IDs in `routeAppFromPathname`.
- `src/desktop/` contains the OS shell:
  - `Desktop.tsx` renders the top bar, shortcuts, windows, dock, and app content.
  - `apps.tsx` defines desktop shortcut and dock metadata.
  - `types.ts` defines valid app IDs.
  - `useDesktopWindows.ts` manages opening, focusing, minimizing, maximizing, dragging, and route persistence for windows.
  - `routeState.ts` validates/persists window search params like `x`, `y`, `minimized`, and `maximized`.
- `src/apps/` contains the actual app UIs. Each app should live in its own folder when it has non-trivial UI or data logic, for example `src/apps/skills/SkillsApp.tsx`, `src/apps/github/GithubApp.tsx`, and `src/apps/strava/StravaApp.tsx`.
- `home.mdx` and `cv.mdx` are route-backed documents inside the generalized `notes.app`. Their shared UI lives in `src/apps/notes/NotesApp.tsx`.
- `src/styles.css` contains Tailwind v4 setup, theme tokens, global styling, and desktop visual primitives.
- `src/routeTree.gen.ts` is generated by TanStack Router. Do not hand-edit it; running the dev server or build regenerates it after route changes.
- `public/` contains static assets such as portraits, icons, manifest files, and favicon assets.

## Adding A Desktop App

When adding a new app, follow the existing route-backed desktop pattern:

1. Add the app ID to `AppId` in `src/desktop/types.ts`.
2. Add desktop shortcut and/or dock metadata in `src/desktop/apps.tsx`.
3. Add an opener and render branch in `src/desktop/Desktop.tsx`.
4. Add a file route in `src/routes/<app>.tsx` using `desktopSearchValidator`.
5. Add the pathname mapping in `routeAppFromPathname` in `src/routes/__root.tsx`.
6. Put the app UI under `src/apps/<app>/`.
7. Run `pnpm build` or the dev server to regenerate `src/routeTree.gen.ts`.

For another note-style document, prefer extending `notes.app` instead of creating a separate app. Add the document ID to `NotesDocumentId`, add a shortcut if needed, add a route that maps to `{ app: 'notes', document: '<id>' }`, and render the document in `NotesApp`.

## Design Direction

- Keep the first screen as the desktop, not a landing page.
- Apps should feel like compact, useful desktop tools: dense enough to scan, clear enough to understand, and visually consistent with the OS shell.
- Reuse existing visual language: rounded windows, title bars, dock buttons, translucent panels, compact headings, and lucide icons.
- Avoid unrelated refactors when adding new apps. Keep changes scoped to the relevant app, route, and desktop wiring.
- Prefer real data and specific content over placeholder copy. If an app is not implemented, mark it clearly as coming soon in `apps.tsx`.
- Make layouts responsive. Desktop windows should remain usable on mobile-sized viewports, even though the concept is desktop-inspired.

## Commands

- `pnpm dev` starts the local Vite/TanStack Start dev server on port `3000`.
- `pnpm build` builds the client, SSR output, Nitro server, and regenerates route artifacts.
- `pnpm test` runs Vitest.

## Working Notes

- The project uses React 19, TanStack Start/Router, Vite, Tailwind CSS v4, Motion, and lucide-react.
- For route/search behavior, prefer TanStack Router primitives and the existing desktop helpers over ad hoc URL handling.
- If you add a new route file, expect `src/routeTree.gen.ts` to change after build/dev. That is normal.
- Some apps fetch live data, such as GitHub and Strava. Keep data-loading concerns inside their app folders unless the route needs a loader.
- Preserve user changes in the working tree. Do not revert unrelated files.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
